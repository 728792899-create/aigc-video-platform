# 备份与恢复手册

本手册区分三种不同能力：项目草稿快照、应用数据库备份、完整灾难恢复。它们的覆盖范围不同，不能互相替代。

## 备份范围

| 能力 | 包含 | 不包含 | 适用场景 |
| --- | --- | --- | --- |
| 项目快照 | 单项目脚本和分镜状态 | 其他项目、完整设置、所有媒体 | 内容编辑回滚 |
| `.aigcbak` | SQLite、非敏感配置 | Keychain/DPAPI 密钥、媒体目录 | 升级或设置恢复 |
| 完整备份 | `.aigcbak`、媒体目录、必要日志摘要 | Provider 密钥和签名凭据 | 换机、磁盘故障、发布前回滚 |

## 为什么密钥不进入备份

桌面版凭证由 Electron safeStorage 加密，并与普通设置分离。备份接口使用脱敏配置，信封明确标记：

~~~json
{
  "magic": "AIGC_BACKUP",
  "version": 1,
  "createdAt": 0,
  "secretsIncluded": false,
  "config": {},
  "db": "<base64 SQLite>"
}
~~~

恢复后需要用户在目标系统重新配置 Provider 密钥。这避免把受操作系统账户保护的密文误当成可迁移秘密。

## 创建应用备份

在设置页选择“备份”，保存扩展名为 `.aigcbak` 的 JSON 文件。文件包含完整项目数据库，因此仍可能含有项目名称、脚本和提示词，应当按用户数据保护。

接口等价行为：

~~~text
GET /api/settings/backup
~~~

备份前建议：

1. 等待当前写入操作完成；
2. 确认没有正在执行的导出；
3. 记录应用版本和 schema 版本；
4. 将文件保存到不公开同步的位置；
5. 不把备份附到公开 Issue。

## 同步备份媒体

`.aigcbak` 不含图片、音频、字幕或视频文件。完整备份需要同时复制应用数据目录中的 `data/uploads`。

~~~mermaid
flowchart LR
  Pause["等待长任务到安全检查点"] --> AppBackup["导出 .aigcbak"]
  AppBackup --> Close["关闭应用"]
  Close --> Media["复制 data/uploads"]
  Media --> Manifest["记录版本、时间和文件数量"]
  Manifest --> Verify["抽查数据库与媒体来自同一批次"]
~~~

不要在应用持续写入媒体时直接做不一致的目录快照。数据库和媒体目录应使用同一时间点标签。

## 恢复应用备份

恢复是高风险操作，会热替换当前内存数据库和非敏感配置。执行顺序：

1. 先为当前数据创建新的安全副本；
2. 在设置页选择要恢复的 `.aigcbak`；
3. 应用验证 magic、数据库内容和 schema；
4. 当前数据库复制为 `restore-point-*.sqlite`；
5. 临时打开备份并执行完整性检查；
6. 原子替换数据库并热加载；
7. 重新打开项目并运行资产健康检查。

~~~mermaid
sequenceDiagram
  participant User as 用户
  participant UI as 设置页
  participant API as Restore API
  participant Check as SQLite 校验
  participant Disk as 数据目录

  User->>UI: 选择 .aigcbak
  UI->>API: POST /api/settings/restore
  API->>Check: 校验 magic / base64 / schema
  Check->>Disk: 创建 restore-point
  Check->>Check: integrity_check
  Check->>Disk: 临时文件 + 原子替换
  API-->>UI: 热加载完成
~~~

如果备份 schema 高于当前程序支持版本，恢复会拒绝继续。先升级应用，不要绕过检查。

## 恢复媒体目录

应用关闭后，将同一批次的媒体副本恢复到目标 `data/uploads`。不要把一个数据库与另一个时间点的媒体混合。

恢复后检查：

- 每个分镜选择的图片存在；
- 音频和字幕路径可访问；
- 成片库记录对应文件存在；
- 外部导出副本可以缺失，但应显示明确状态；
- 资产健康检查没有悬空 selected image；
- 能成功执行一次预览和测试导出。

缺失媒体时不要直接编辑数据库路径。使用文件恢复、重新生成或工作台修复入口。

## 迁移前自动备份

数据库升级时，如果 `PRAGMA user_version` 低于当前 schema，程序会先写入：

~~~text
data/backups/database-v<旧版本>-<时间戳>.sqlite
~~~

自动轮换保留最近五份。这些文件只保护数据库迁移，不包含媒体，也不是用户主动创建的完整备份。

## 换机流程

1. 在旧机器导出 `.aigcbak`；
2. 关闭应用并复制完整 `data/uploads`；
3. 在新机器安装相同或更高版本；
4. 启动一次后关闭，确认新数据目录；
5. 恢复 `.aigcbak`；
6. 关闭应用并恢复媒体目录；
7. 重新配置 Provider 密钥；
8. 运行资产健康检查和 Demo 导出；
9. 保留旧机器数据，直到验收完成。

## 发布前恢复演练

每个候选版本至少完成一次：

- [ ] 从当前版本创建备份；
- [ ] 创建或修改一个测试项目；
- [ ] 恢复备份并确认修改被回滚；
- [ ] 验证项目、分镜、图片和成片记录；
- [ ] 验证凭证没有随备份恢复；
- [ ] 验证 restore point 已创建；
- [ ] 验证一条长任务可以继续或给出诊断；
- [ ] 导出一个有效 MP4；
- [ ] 清理演练用测试数据。

## 故障处理

| 现象 | 处理 |
| --- | --- |
| “不是有效的备份文件” | 检查 magic 和文件是否被二次包装或截断 |
| schema 版本过高 | 升级应用后再恢复 |
| 完整性检查失败 | 保留原文件，换另一份备份，不强制替换 |
| 项目存在但图片缺失 | 恢复匹配的 uploads，或执行单阶段修复 |
| 恢复后 Key 为空 | 这是设计行为，在系统安全存储中重新配置 |
| 成片记录存在但外部副本缺失 | 检查成片库受管文件，必要时重新导出 |

提交恢复问题时只提供应用版本、schema、错误摘要、请求 ID 和经过脱敏的文件统计。不要上传备份本身。
